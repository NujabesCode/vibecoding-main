# 우리반 캠퍼스 · 구조 설명서

> 이 코드를 처음 보는 개발자를 위한 문서. 정찰 버전(step-1) 기준으로, 코드를 보고 작성했다.

## 한 줄 요약

브라우저에서 픽셀 캐릭터를 꾸미면 그 디자인(JSON 한 덩어리)을 스프링 서버가 MySQL에 저장하고, 로비에서 반 친구들 캐릭터를 모아 보여준다.

## 폴더 구조와 핵심 파일

```
backend/                      스프링부트 3.5 (Java 21, Gradle)
  player/Player*.java         닉네임으로 입장 → 플레이어 생성
  character/Character*.java   캐릭터 디자인 저장/조회
  resources/db/migration/     Flyway 마이그레이션 (V1__init.sql)
frontend/                     리액트 19 + Vite + TypeScript
  src/engine/                 그림 엔진 (리액트와 무관한 순수 함수)
    color.ts                  색 팔레트, 그림자/하이라이트 색 계산
    sprite.ts                 32x48 레이어 → 걷기 4프레임 합성, 외곽선
    parts.ts                  헤어/눈/상의/하의/소품을 픽셀로 그리는 곳
    design.ts                 디자인 ↔ JSON 변환 (RLE 압축)
    classroom.ts              미리보기 교실 배경
  src/pages/                  Entry(입장) · Lobby(로비) · Studio(공방)
  src/components/             Walker(제자리 걷기) · RoomPreview(교실 미리보기)
  src/api.ts                  서버 호출은 전부 여기
  src/session.ts              내가 누구인지 localStorage에 기억
docker-compose.yml            개발용 MySQL 8.4
```

## 데이터가 흐르는 순서

1. **입장**: 닉네임 입력 → `POST /api/players` → `{id, nickname}`을 받아 localStorage에 저장
2. **공방**: `GET /api/characters/{내 id}` → 있으면 불러오고 없으면 기본 캐릭터
3. **그리기**: 모든 편집은 브라우저 메모리의 `Design` 객체에서 일어난다. 서버는 모른다.
4. **저장**: `PUT /api/characters/{내 id}` 에 `design`(문자열 JSON)을 통째로 보낸다
5. **로비**: `GET /api/players` + `GET /api/characters` 를 합쳐 친구 카드를 그린다

## 캐릭터 그림은 어떻게 만들어지나

- 캐릭터 한 장은 32x48 픽셀, 방향은 앞(down)·옆(side)·뒤(up) 세 개. 오른쪽은 옆을 뒤집어서 만든다.
- 방향마다 레이어 9개: 액세서리, 머리카락, 얼굴, 머리, 왼팔, 오른팔, 몸통, 왼다리, 오른다리
- 픽셀 값은 색이 아니라 **물감 코드**(`h0`=머리 기본색, `t1`=상의 그림자 …). 그래서 팔레트만 바꿔도 직접 그린 부분까지 색이 같이 바뀐다.
- 걷기 애니메이션은 따로 그리지 않는다. `frameOffset()`이 레이어를 1~2픽셀씩 옮겨서 4프레임을 만든다.
- 외곽선, 이마 그림자는 `compose()` 마지막에 자동으로 붙는다.

## 내가 내린 결정과 이유

| 결정 | 이유 |
|---|---|
| 디자인을 JSON 문자열 하나로 저장 | 레이어 구조가 아직 자주 바뀔 것 같아서 테이블로 쪼개지 않았다 |
| 픽셀을 RLE로 압축 | 3방향 × 9레이어 × 1536칸을 그대로 넣으면 수백 KB라서 |
| 그림 엔진을 리액트 밖 순수 함수로 | 테스트하기 쉽고, 나중에 메타버스 화면에서 그대로 재사용하려고 |
| 해시 라우팅(`#studio`) | 라우터 라이브러리 없이 새로고침해도 페이지가 유지되게 |
| Flyway 마이그레이션 | DB 구조 변경을 기록으로 남기려고. `ddl-auto`는 `validate`만 |

## 임시방편으로 때운 곳 · 확실하지 않은 곳 (찜찜한 곳)

1. **아무나 남의 캐릭터를 덮어쓸 수 있다.** `PUT /api/characters/{playerId}`는 요청한 사람이 그 플레이어인지 확인하지 않는다. 주소의 숫자만 바꾸면 된다.
2. **"로그인"이 없다.** 브라우저가 기억하는 건 `{id, nickname}`뿐이라, 개발자 도구에서 id만 바꾸면 다른 사람이 된다.
3. **디자인 크기 제한이 없다.** 아주 큰 문자열을 보내도 그대로 DB에 들어간다.
4. **서버가 디자인 내용을 검사하지 않는다.** 깨진 JSON도 저장된다. 프론트의 `parseDesign`이 걸러서 화면이 죽지는 않지만, DB에는 쓰레기가 쌓일 수 있다.
5. **닉네임 검사가 없다.** 빈 문자열도 되고, 20자를 넘으면 DB에서 에러가 나서 500이 뜬다.
6. **목록 API가 전부를 한 번에 준다.** `GET /api/characters`가 모든 디자인을 통째로 내려준다. 30명이면 괜찮지만 많아지면 느려진다.
7. **테스트가 하나도 없다.**
